Rules every proposal follows

  • Reminders and notifications are calm. An ordinary reminder (“brake fluid in 3 weeks”) uses neutral or soft-amber styling and a short sentence. Red is kept for a fault the car itself reports or for something unsafe to ignore.
  • Text sizes: page title 24–30, section title 18–22, body 15–17, helper and status text 13–15, nothing a person must read below 12. Only unit tags and chart axis labels may be 11.
  • Long translations wrap onto more lines; no fixed-height label holds a sentence.
  • Light and dark themes are designed together; the wireframes on this page switch with the system theme.
  • One icon style (outline, one stroke weight) across the app, and no emoji-style icons anywhere — see “Icon direction” below.

Icon direction

Policy: NO EMOJI-STYLE ICONS IN THE OBD360 USER INTERFACE. This page contains none either; every icon below is drawn from the app’s own outline set.

Rules

  • Text first. Many elements need no icon: a clear label or a status word (“Ready”, “Not reported by this car”, “Needs attention”) is better than a symbol.
  • Where an icon helps (close, expand, chevron, play / pause, record, filter menu, favourite, status check / warning / info) it comes from one catalog: monochrome outline, 24-unit grid, round caps, one stroke weight, colour = text colour or a single status colour.
  • No emoji, no Unicode symbols standing in for icons (check marks, crosses, stars, bullets, arrows, flags), no coloured pictograms, no flag images for languages (a two-letter code is used).
  • Status is never carried by colour or an icon alone — the word stays next to it, and every icon-only button has an accessibility label.
  • Light and dark: icons use the text colour, so they follow the theme; status colours use the same tokens as the pills.
  • Kept as they are: the OBD360 logo, manufacturer logos, real graphs, gauges, diagrams and vehicle photos.

What replaces what

  • Emoji on fuel / electric badges → words (“Engine running”, “On electric”) in a pill.
  • Language flags → “KA”, “EN”, “DE” … code badge.
  • Check / cross / dot prefixes in lists → icons in a fixed column, or just the word.
  • Text arrows used as chevrons and close buttons → .

1 · Mileage verification

Today: Views/MileagePage.xaml, Services/Mileage/*. The analysis layer already separates total odometer from context values and treats zero or out-of-range values as "flagged, not used".

What looks wrong

  • The result mixes the verdict, the per-source table and the technical log on one long scroll.
  • "Not requested", "PID not advertised", "no definition" and "no answer" look alike in the list although they mean different things.

Proposal

  • One headline card: Consistent / Single source / Conflicting / No reading, never a "true mileage".
  • A source list grouped by outcome with fixed colours: Confirmed · Unverified · Not supported · Not requested · PID not advertised · No definition · Communication failed · No data · Insufficient data.
  • Zero and implausible values shown only under "Values to review (not used)".
  • Technical log collapsed behind a “Technical log” row with a disclosure icon.

Data rules kept

  • No estimate is ever shown as a reading; only total-odometer values are compared; nothing is written to the car.

Decision needed

  • Group by outcome (proposed) or by control unit?

Icons

  • Source outcomes are written as words in the pills; no check / cross prefixes.
  • The “Read again” action uses ; the collapsed technical log uses a disclosure icon.

2 · Fuel consumption

Today: Views/FuelPage.xaml, ViewModels/FuelViewModel*.cs — one screen for petrol, diesel, hybrid and EV.

What looks wrong

  • An engine-off hybrid or an EV looks like a fuel page with empty fuel fields.
  • The fuel average and the engine-on figure are easy to mix up.

Proposal

  • The page opens in the mode that matches the powertrain: Combustion · Hybrid · Plug-in · Electric.
  • Hybrid: two clearly separated blocks — fuel (whole trip) and battery (used / recovered / net), plus a one-line note about what each average divides by.
  • Electric: kWh, kWh/100 km, recovered by braking; no fuel widgets at all.
  • Missing data shown as "not reported by this car", never as 0.

Decision needed

  • Should a plug-in hybrid show the electric-only km separately (proposed)?

Icons

  • No fuel-pump or lightning pictograms: the two blocks are titled “Fuel” and “Battery” in words, and the drive-state chip reads “Engine running” or “On electric”.
  • The trip-summary card closes with .

3 · Inspection readiness

Today: Views/TechnicalInspectionPage.xaml — nine question categories plus an OBD check.

What looks wrong

  • The result words ("likely to pass", "unlikely to pass") sound like a promise; the official centre decides.
  • The OBD part and the questionnaire are mixed in one score.

Proposal

  • Two separate rows: OBD check (automatic) and Physical inspection (owner's answers).
  • A single, calm summary: "No known problem found", "Needs attention", "Dangerous fault — repair first", "Not finished yet".
  • The disclaimer stays visible: preliminary assessment, not a guarantee.

Icons

  • Result is a word (“Needs attention”) with at most one / icon inside the badge; no check-mark characters as list prefixes.

4 · ECU Explorer

Today: Views/ModuleScanPage.xaml, EcuIdentifiersPage, ModuleLiveDataPage.

What looks wrong

  • A silent address is easy to read as "module absent" although it only means "no reply".

Proposal

  • Cards per module with one of four states: Answered · Incomplete reply · Technical failure · No reply (this does not prove the module is absent).
  • Names marked "from address table" when the module did not report its own name.
  • A sticky summary: answered / incomplete / failed / silent counts.

Icons

  • The four module states are words (Available · Limited · No reply · Not supported) with their pill colours; the dot / half-dot / ring glyphs are gone.
  • The bus tree keeps its drawn connector lines; that is a diagram, not an icon.
